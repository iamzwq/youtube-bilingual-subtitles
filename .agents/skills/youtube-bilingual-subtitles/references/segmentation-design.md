# 断句设计说明（为什么这么切）

本文解释 `segment.py` 的原子化（atoms）设计取舍，回答几个常见「为什么」。核心思想一句话：**把「精确时间」和「语义断句」解耦，机器和 LLM 各做擅长的部分，atoms 是两者之间的接口。**

## 1. 为什么要切成细粒度 atoms，输出 `raw_segments.json`？

先看两个不可行的极端方案：

- **直接用 YouTube 原始字幕分行**：自动字幕是滚动式的（同一批词在多个 event 里重复逐词追加），分行按「显示区域」而非语义切，既有重复又不能当字幕条用。
- **整段丢给 LLM，让它自己断句 + 自己算时间**：LLM 不可靠地处理毫秒时间戳，极易算错、错位、累积漂移；时间戳数据量大，塞进 prompt 费 token 又易被改坏。

atoms 方案的解法：`segment.py` 先把字幕切成「每个约几个词、**带精确起止时间**」的原子块，编上索引 `i`。LLM 断句时**不碰时间**，只引用 atom 的**索引区间**；`build_ass.py` 再用 `atoms[起].start → atoms[止].end` 反推真实时间。

| 难点                  | 交给谁                 | 为什么                       |
| --------------------- | ---------------------- | ---------------------------- |
| 毫秒时间精度          | 机器（atoms 已带时间） | 机器精确，LLM 算不准         |
| 语义断句 / 长短句取舍 | LLM（只写索引区间）    | LLM 懂语义，且只需输出小整数 |

atoms 越碎，LLM 可选的切点越多、断句自由度越高，所以 atomizer **故意切得很碎、不承担语义断句**。

## 2. word 模式：为什么不「一词一 atom」切到最碎？

一词一 atom 自由度最大，但成本与收益不成正比：

**成本**

- **数量爆炸**：10 分钟视频有几千个词 → LLM 要引用几千个索引区间，还要保证「首尾相接、不重叠、不遗漏」，覆盖记账出错面随数量线性上升。
- **token 浪费**：每个 atom 带 `i/start/end/text` 四字段，条目越多上下文越贵。

**收益**

- 断句真正需要的切点几乎都落在**自然边界**上，而 atomizer 的 flush 条件正是卡在这些边界：

| flush 条件             | 常量            | 含义                             |
| ---------------------- | --------------- | -------------------------------- |
| 词间停顿               | `GAP_MS=400`    | 换气/停顿——最可能的语义切点      |
| 句末标点               | `SENT_END`      | 句子结束                         |
| 词数 / 字符 / 时长上限 | 8 / 45 / 3000ms | 兜底，防某段无停顿导致 atom 过长 |

**结论**：不是越碎越好，而是「碎到把所有可能的语义边界都变成 atom 边界」就够了。唯一残留风险：真正的切点落在某 atom 中间（被词数上限凑在一起、中间又无停顿），LLM 就切不动；但这种情况很少，代价只是那一处断句略粗。

## 3. event 模式：没有词级时间，怎么切？

走 `atoms_from_events` + `chunk_text`，分两步：

1. **按文本切块**（`chunk_text`）：逐词累加，命中「≥8 词 / ≥45 字符 / 句末标点」就切一块——只看文本，不看时间。
2. **按字符数比例分摊时间**：一个 event 只有整块 `[start, end]`，把 chunks 按字符长度占比线性瓜分这段时间（假设语速均匀，一块占 30% 字符就分给它 30% 时长）。

**关键差异**：event 模式下把 atom 切得更细**不会提升时间精度**（时间是插值猜的），切细只会让同一段猜测的时间分得更零碎、边界噪声更大。切块的意义只剩「给 LLM 断句自由度」。

## 4. 句末标点 vs 句中标点：为什么只按句末切？

`segment.py` 的 `SENT_END` 只含**句末**标点（`. ! ? 。 ！ ？ …`）；逗号/分号/冒号**不触发切分**，原样留在 atom 内部。原因是二者性质不同：

- **句末标点 = 无歧义的硬边界**：一句话结束，在这里切 atom 永远安全，机器可放心当硬规则。
- **句中标点 = 要看语义的软边界**：是否好切取决于上下文——`我们做了个应用，然后发布了`（并列分句，适合断）vs `又快、又稳、又便宜的方案`（短语内部，切了就割裂）。判断这个差别需要语义理解，机器用简单规则容易切错。

原则：**只在「怎么切都不会错」的点切 atom，需要判断的点让给 LLM**。句中标点并非被忽略，而是在 LLM 断句步骤（见 SKILL.md 3b）中作为**默认必断的边界**处理：出现逗号/分号/冒号（或连词之前）即断句，优先级与句末标点同级，**唯一例外**是断开后某侧片段 ≤3 词才免断。之所以在 atomizer 里不硬切句中标点、却在 LLM 步骤里要求必断，是因为 atomizer 只有简单规则、易误伤短语内部的顿号式逗号，而 LLM 有语义判断力，能识别"该断的逗号"与"短语内部不该断的逗号"。

**两种模式的实际影响**：word 模式（自动字幕）几乎无标点，真正驱动切分的是停顿 `GAP_MS`，而逗号处人通常会停顿，那里已有边界，故无影响；event 模式有完整标点，逗号若落在 atom 中间且被词数上限凑住，LLM 就只能在最近的 atom 边界断——这是个小限制，但 event 模式时间本就是近似，影响有限。

## 小结：为什么优先 word 模式

同样是切碎给 LLM 断句，word 模式的每个 atom 边界都**锚定在真实音频时间**上（停顿即真实时刻），成品字幕时间轴贴得准；event 模式的 atom 时间是按字符比例插值的近似。这正是本 skill 始终优先自动字幕、缺失才回退人工字幕的根本原因。
